# Audit campaign — operator runbook

A rolling, resumable campaign of agent batches over the SKU links. Its products, in priority order:
**curated hard-negative ignores**, missed links (recall), and wrong links (precision). Every batch is
one agent-sized file; `audit/campaign/manifest.json` records every batch's state, so the work can stop
at any step and resume a week later from a fresh session. There is always a "next most valuable
batch": `node tools/audit_campaign.js next`.

Companions: `docs/audit-runbook.md` (the agents' decision protocol), `docs/audit-full-library-plan.md`
§6–7 (agent cost and operating rules), `.worktrees/data/data/sku_link_policy.md` (the owner's rules).

**The campaign never commits, pushes, uploads a Release, or touches the shipped model** (`gbt_model.json`
in the worktree, `tools/linker_ml/out/*.json`, the checkpoint, `MODEL_VERSION`). Its retrains write only
to `tools/linker_ml/out/campaign/round-N/`. The owner commits `data/sku_links.json`.

## Files

| path | what |
|---|---|
| `tools/audit_campaign.js` | the CLI (`init`, `generate`, `mine`, `status`, `next`, `mark`, `coverage`, `collect`, `round-close`) |
| `audit/campaign/manifest.json` | rounds, batches, statuses, yields, tokens, metrics. Written atomically under `manifest.lock` |
| `audit/campaign/frozen_split.json` | the held-out sku set pinned at round 0 |
| `tools/audit_campaign_prompt.md` | the agent prompt (tracked); `next` renders it per batch |
| `audit/campaign/round-N/` | `rich-default.jsonl`, `rich-wide.jsonl`, `work/` (scored neighbour/sibling pairs), `batches/`, `proposals/`, `decisions/`, `scratch/<batch>/` |
| `tools/linker_ml/out/campaign/round-N/` | that round's dataset, features, GBT, OOF scores, `views/` (honest rows), `frozen_metrics_{cut,new}.json` |

`audit/` and `tools/linker_ml/out/` are git-ignored.

## 1. Check state (fresh session)

```bash
git -C .worktrees/data status --short          # dirty data/sku_links.json = applied, not yet committed
node tools/audit_campaign.js status            # rounds + metrics, every batch, yields, tokens
```

`running` batches are agents that were launched and have not been collected. If their agents are still
in this session, resume them (§3); if the session that launched them is gone, look for their output
files: if the decisions file passes `coverage`, `mark <b> done`; otherwise `mark <b> failed --note …`
and the next `mine` re-offers those pairs (failed and stale batches are not excluded).

**If Node tools that import `viz/app` crash** (front-end code that reads `document` at import; it happened
while the PWA work was uncommitted, and imports work again at `b91c4608`), run the campaign from a clean copy of an earlier commit with the campaign files copied in:
`git archive <good-sha> | tar -x -C <scratch>/clean`, copy `tools/audit_campaign.js` and its changed
dependencies over, and symlink `<scratch>/clean/{audit,.worktrees/data,tools/linker_ml/out,tools/linker_ml/.venv}`
to the real ones. Every path in the manifest is repo-relative, so either copy reads it.

## 2. Inputs, generate, mine (once per round)

Refresh the Release assets first; pulling `data` refreshes none of them (plan §7):

```bash
W=.worktrees/data/viz/data
gh release view embeddings-latest --json assets --jq '.assets[] | "\(.name) \(.updatedAt)"'   # must be < ~1 day old
curl -sfL -o $W/index.json https://github.com/brennanwilkes/spirit-tracker/releases/download/index-latest/index.json
curl -sfL -o $W/sku_embeddings.json https://github.com/brennanwilkes/spirit-tracker/releases/download/embeddings-latest/sku_embeddings.json
curl -sfL https://github.com/brennanwilkes/spirit-tracker/releases/download/skus-latest/skus.tar.gz | tar xz -C $W
rm -f audit/.cache/history_surface.json
```

Generate both rich files (run in the background; they print progress every 2,000 listings):

```bash
node tools/audit_campaign.js generate --round N --profile default    # ~9 min, ~730 MB
node tools/audit_campaign.js generate --round N --profile wide       # ~30 min, ~0.9 GB
```

`wide` = `AUDIT_POOL_EMB=1`, pool 2000/400, rerank cuts 1000/250, `--top 10`. Measured on a 400-listing
sample (2026-10-01): it adds the mid- and low-band pairs (+3 in 0.2–0.5, +15 in 0.05–0.2, +194 in
0.01–0.05 per 400 listings vs `--top 15` alone) and contains every ≥ 0.01 pair of the default pool
but one. Raising `--top` alone adds only pairs below 0.01. `--model round-M` scores with an earlier
round's candidate GBT instead of the shipped one (`LINKER_GBT_MODEL`); the default is the shipped model.
`generate --register` records a rich file that was generated by hand.

Then mine (dry-run first; ~2 min plus ~1 min of live scoring on a first run):

```bash
node tools/audit_campaign.js mine --round N --dry-run
node tools/audit_campaign.js mine --round N
```

`node tools/audit_campaign.js discard --round N` drops a round's batches (files and manifest entries)
while every one of them is still `pending`, and restores `precisionSince`, so a round can be re-mined
after a tooling change at no cost.

### What `mine` does

Sources (`--sources`, default all):

| source | what |
|---|---|
| `pool` | candidates + title twins in `rich-default` |
| `wide` | the same from `rich-wide` |
| `emb` | every catalog sku's 8 nearest embedding neighbours (`--emb-k`) that are neither linked nor ignored, scored live (`audit_new_listings.js --emb-neighbours`) |
| `sibling` | same family name (title minus age/size/ABV/year/edition/bottler words), different canonical group, at most one parsed attribute apart; scored live (`--score-pairs`) |
| `precision` | WHOLE groups touched by a CI auto-link written since the round's `precisionSince` (round 1: 2026-09-24), via `audit_link_group_slice.js --auto-since` |
| `labels` | existing links/ignores the previous round's out-of-fold model disagrees with most (≥ 0.5, top 200, frozen split excluded) |

Every pair is dropped when it is already decided: in one canonical group, ignored at the canonical
level, or in any earlier non-failed campaign batch. Live scores use the same `buildEnv` + GBT blend as
production (`scoreAgainst` in the generator), in both directions; `prob` is the max (CI links when
either direction clears the bar).

**Brand screen (since round 2):** a canonical group pair is dropped when no member pair's names share a brand
word: a distinctive word, or a bigram of two generic words ("canadian club", "old malt"), with possessives and
plurals folded (`brandTokens` in the tool). Sibling-source pairs always pass. Different brands that share only a
format or a style word are correct rejections but worthless labels.

**One item per canonical group pair.** A link or an ignore is a decision about two canonical groups, so
`mine` collapses every unjudged member pair between the same two groups into ONE item. The
representative is the highest-value member pair (bucket order, then prob); the others ride along in
`also[]` as `[a, b, prob]`, including ones below the value floor. The agent decides once. On a reject it
emits an ignore for the representative AND every `also[]` pair: they are separate training rows, so
each one is a hard negative. On an accept, one link is enough. Verdict `split` (with a note) covers a
group where one member is clearly a different product. `coverage` enforces all three rules. Each group
pair is in exactly one batch (`mine` asserts it), and later mines exclude every member pair of a
non-failed, non-stale batch.

Value order (each item also carries a `cls` tag — the attributes the parsed names differ on):

| bucket | rule (on the representative) | tier | per-item estimate (+80 per `also[]` pair) |
|---|---|---|---|
| B0 | prob ≥ 0.95, unjudged (CI would link it today) | A | 0.9K |
| B1 | 0.5–0.95 | A | 0.9K |
| B2 | 0.2–0.5 | A | 0.9K |
| B3 | 0.05–0.2 | B | 0.6K |
| B4 | < 0.05 but confusable: a sibling pair, embedCos ≥ 0.85, or det ≥ 4 | C | 0.4K |
| B5 | the remaining 0.01–0.05 | D | 0.55K |
| — | < 0.01 and not confusable | dropped | — |

Batches never mix tiers. Within a tier, items whose canonical groups touch are kept together, strongest
neighbourhood first. A batch holds at most 400K tokens of estimated decision cost (480K end context
minus the 80K fixed cost) and 650 KB, and the batches of a tier are filled evenly. Every 3rd slot goes to a precision/label batch. The per-decision numbers for tiers B–D are
estimates; compare `est tok` with the recorded `tokens` in `status` after the first batch of each tier
and change `TIERS[].perItem` in the tool before the next mine.

## 3. Launch batches

```bash
node tools/audit_campaign.js next --n 4
```

For each batch it prints the file, the `mark … running` command and the full rendered prompt. Then,
per batch: `node tools/audit_campaign.js mark <b> running --note "agent <id>"`, and launch an Agent with
`subagent_type: general-purpose`, `run_in_background: true` and the printed prompt verbatim.

- **At most ~4 concurrent agents.**
- **A session-limit stop is not a failure: resume each stopped agent in place with `SendMessage`**
  ("continue where you stopped; your outputs so far are in …"). Never relaunch a batch whose agent can
  still be resumed — a relaunch pays the fixed cost twice and can write a second proposal.
- The agent ends with a `CAMPAIGN-RESULT {…}` line and writes the same JSON to `proposals/<b>.result.json`.

## 4. Collect (serial)

When an agent completes, its notification carries `subagent_tokens` (end-of-run context):

```bash
node tools/audit_campaign.js coverage <b>                 # every item decided exactly once
node tools/audit_campaign.js mark <b> done --tokens <subagent_tokens>
node tools/audit_campaign.js collect <b>
```

`collect` refuses unless: coverage passes; the worktree is not behind `origin/data` (it fetches first;
`--no-fetch` skips that); nothing but `data/sku_links.json` / `sku_links_auto.json` is dirty; and, if
those are dirty, they are byte-identical to what the campaign's last `collect` wrote. It then runs
`validate_proposal_skus.js --fix`, a dry-run, and `apply_audit_proposal.js --apply` (main proposal,
then the label batch's `.followup.json`). It refuses a proposal that would group an ignored pair. Each
proposal file's counts (links, ignores including every `also[]` ignore, unlinks, remove-ignores, review,
data quality, ineffective unlinks) are recorded in `batch.applied` as soon as it applies. A re-run after
a partial failure skips the files already applied, provided they are unchanged (it refuses if one
changed), and sums the recorded counts, so the yield is never under-counted. **Model wrong** = the
agent's verdict disagrees with the representative's `prob ≥ 0.5`. Then the batch is marked `applied`.

Collect one batch at a time; `collect` holds the manifest lock, so two cannot interleave. No two batches
share a canonical group pair, so they cannot give one pair two verdicts. But they are not independent:
a link in one batch can merge groups that another batch's link would then join to an ignored group. The
applier's transitive check stops that second apply; resolve it in that batch's proposal. A merge step
(`tools/merge_audit_proposals.js`) is not needed.

Read each batch's `review[]` (the applier echoes it in the report) and keep a list for the owner.

## 5. Ask the owner to commit

After a collect, `data/sku_links.json` is dirty. **The owner commits it on `data` before the next cron
run** (CI cannot see an uncommitted ignore, and a `git pull` over the dirty file drops it — plan §7).
Big cron runs commit at ~00:00 and ~12:00 PT, small ones every ~3 h, so collect in a burst and ask
right away. Then:

```bash
node tools/audit_campaign.js mark all-applied committed   # refuses while the link files are still dirty
```

If CI pushed meanwhile, `collect` refuses (worktree behind `origin/data`) until the owner has committed,
pulled and pushed.

## 6. Close a round, re-mine

Close a round when its batches are collected (or failed) — or earlier, whenever ~1,000 labels have
landed and a fresh model would re-rank the frontier. Refresh `sku_embeddings.json` first (§2), so the
features see the current groups.

```bash
node tools/audit_campaign.js round-close N    # ~1–2 min; --allow-open if batches are still out
node tools/audit_campaign.js status
```

It retrains the GBT on the current labels with the frozen split held out, evaluates **both** the
round-0 baseline model and the new model on the current labels restricted to the frozen split, records
recall at 99% precision, AUC+, precision and recall at the 0.95 bar and labels added, and opens round
N+1. Then §2 again for round N+1 (optionally `generate --model round-N` to mine the new model's
frontier). `precisionSince` advances to the last precision mine, so new CI auto-links keep being covered.

**Pending batches of the closed round are marked `stale`** (chosen over carrying them forward: their
probs, buckets and groupings came from the old labels and model). `next` only serves batches of an
open round. A stale batch's pairs are not excluded, so the next round's mine re-offers whatever is still
unjudged, re-ranked.

### The frozen split and why the retrain is GBT-only

- `frozen_split.json` = every catalog sku whose round-0 canonical group hashes into the trainers' own
  TEST bucket (FNV(canon) < 0.15, as in `export_gbt.py` / `train_embed.py`): 2,166 skus / 1,207 groups.
  98.2% of them were already in the TEST bucket of the pre-2026-09-24 dataset, so it is close to the
  groups the shipped encoder never trained on. A pair is frozen when either sku is in the set; frozen
  pairs are never trained on (`export_gbt.py`, `oof_misses.py`) and the `labels` source never offers them.
- Each round's metric is BOTH models on the SAME current-label frozen rows. The before/after inside a
  round is the honest comparison. Absolute numbers move between rounds because the frozen rows gain the
  campaign's new labels (hard examples, by construction).
- **GBT only, on fixed embeddings** (the CI-encoded `embeddings-latest`, i.e. the shipped checkpoint).
  The encoder fine-tune is nondeterministic (two identical runs: mean cosine 0.969, ±130 OOF pairs —
  `tools/linker_ml/CLAUDE.md`), so a per-round encoder retrain would bury the label effect in noise; it
  is slow; it only reaches production through a checkpoint release, which the campaign must not do; and
  keeping it honest would need the frozen split threaded through `train_embed.py`. Fine-tune the encoder
  once, at the owner's next shipped retrain, on the campaign's labels.

### When yield has dried up

Stop a tier when two consecutive batches of it produce fewer than ~5 ignores per 100 items that are not
`noop unrelated`, and no links. Stop the campaign when, in addition, a `round-close` shows the round
model no better than the baseline on the frozen split (rec@99 and AUC+ within noise, ~0.3 pt) for two
rounds running, and the `labels` batches come back mostly `keep`. Record the per-tier yield here when
that happens.
